# ADR 0008：文档里的数字与代码锁死

- 状态：已采纳
- 日期：2026-09-18

## 背景

0.10.0 上线后核对文档，发现两处已经和代码对不上的「硬数字」：

1. `README.md` 写「`npm run check` 目前包含 23 项契约」，实际 `scripts/verify.mjs` 已有 38 项。
2. `docs/RELEASE-RUNBOOK.md` 写「计算 11 个上线文件」，实际 `scripts/deploy.mjs` 的 `FILES` 已有 13 个；
   正文的上线文件清单也漏掉了 `assets/tokens.css` 与 `assets/site.css`。

这类漂移不会让任何测试变红，但会让人按文档操作时得到错误预期：
新增上线文件的人会以为不用改文档，读文档的人会以为只有 11 个文件在发布。
光靠「记得同步文档」不成立，必须让机器来查。

## 决策

### 1. 数字由代码推导，文档只做声明

`scripts/verify.mjs` 现在读取 `README.md` 与 `docs/RELEASE-RUNBOOK.md`，把文档里声明的
「契约数」「上线文件数」与代码里的真实数字比较，不一致即报错。

### 2. 上线文件清单必须覆盖 `deploy.mjs` 的每个文件

除了数量一致，发布文档里还必须逐个出现 `scripts/deploy.mjs` 的 `FILES` 条目，
防止「数量对了但清单漏项」这种更隐蔽的漂移。

### 3. 三条检查只增不减

检查项追加在 `checks` 数组末尾（先算总数再 push，避免数组字面量自引用）。
反向验证确认：把 README 改回 23、把 Runbook 改回 11，验证脚本都会立刻以非零码退出并点名该项。

## 后果

- 改契约数或上线文件数时，忘记同步文档会被 `npm run check` 直接拦下。
- 文档里的数字从此有唯一事实来源（代码），不再依赖人工核对。
- 代价是文档中这两个数字不能再随手写，必须与代码一致；这是有意为之的约束。
